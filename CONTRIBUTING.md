## С чего начать

Нужен Go 1.26+.

```sh
git clone https://github.com/Windemiatrix/go-libs
cd go-libs
make help            # список команд
make test            # все проверки, как в CI (на macOS)
make mod vet cover   # на Linux: то, что запускает Linux-job CI
```

## Путь изменения

Путь одинаков для всех участников: мейнтейнера, внешних авторов (из ветки форка) и Dependabot. Для ИИ-агентов есть отдельные правила — [AGENTS.md](AGENTS.md).

1. Ветка от актуального `main`: `<type>/<тема>`, например `feat/schema-photos12`, `fix/template-parser`. Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`.
2. Сначала тест, потом код (TDD): тест, который падает по нужной причине, затем код, который его проходит. Исправление ошибки начинается с теста, воспроизводящего ошибку. Для портированного поведения тест сверяется с эталоном osxphotos там, где он есть.
3. Перед PR локально зелёный `make test`: он запускает все проверки, включая линтеры. Скрипты оболочки проверяет `shellcheck`, его ставите сами (`brew install shellcheck`); остальные инструменты загружает `go run`.
4. PR в `main`. В описании — что и зачем меняется. Прямых push в `main` нет.
5. Зелёный `ci-ok`: он сводит все обязательные проверки в одну.
6. Слияние — только squash, его делает мейнтейнер. Одобрений пока не требуется, потому что разработчик один; слияние остаётся решением мейнтейнера.

## Заголовок PR

Заголовок PR становится заголовком коммита в `main`.

- Формат `<type>(<scope>)[!]: <описание>`, например `feat(schema): add photos12 schema`. Scope обязателен: строчные латинские буквы, цифры, `._/-`.
- `!` сразу после scope отмечает несовместимое изменение публичного API: `feat(photosdb)!: rename the query options`. Маркер определяет следующую версию (см. «Выпуск (для мейнтейнера)») и переносит заголовок в раздел «Breaking changes» заметок к релизу. Тело squash-коммита пустое, `BREAKING CHANGE:` в нём не распознаётся.
- Английский, только печатные ASCII-символы, не длиннее 70 символов, без `#<номер>`: GitHub сам дописывает ` (#<номер PR>)`.
- Проверяет workflow `pr-title` при открытии PR, каждом push и каждой правке заголовка. До открытия PR заголовок можно проверить локально: `make pr-title PR_TITLE='...'`.
- **В окне squash-слияния заголовок и тело коммита не редактируются.** Править можно только заголовок PR: иначе в `main` попадёт заголовок, который проверка не видела.
- Заголовки коммитов внутри ветки не проверяются: squash их отбрасывает.

Заголовок PR попадает в заметки к релизу: формулируйте его для пользователя модуля. Отдельного списка изменений нет.

## Красный `ci-ok` на `main`

История `main` не переписывается: force-push и удаление запрещены, теги неизменяемы. Красный `ci-ok` на `main` чинится следующим PR.

## Зависимости

Новая прямая зависимость — отдельный PR с обоснованием: зачем она нужна, почему не хватает стандартной библиотеки, какая у неё лицензия (совместимая с MIT) и как она сопровождается. `go.mod` и `go.sum` проверяет мейнтейнер.

## Язык

- Код, комментарии, сообщения коммитов и заголовки PR — на английском.

## Личные данные и тестовые материалы

Публичная история необратима: форки и архивы сохраняют всё, что однажды попало в репозиторий. В коммиты и PR не попадают:

- ваши библиотеки «Фото» и любые их копии или выгрузки, названия ваших альбомов, пути, UUID и GUID, точные числа вашей медиатеки;
- пароли и токены.

В `testdata/` лежат только `database/Photos.sqlite` тестовых медиатек с проверенной лицензией и синтетические фрагменты; изображения не копируются. `testdata/` лежит вне каталога модуля и в zip модуля не входит; каталог `osxphotos/` входит в zip целиком, поэтому тестовые данные в него не кладутся. Эталоны не правятся вручную: их создаёт отдельный ручной workflow из зафиксированной версии osxphotos.

В тестах и документах — обобщённые примеры: `IMG_0001.HEIC`, `2024/05-01 - Holidays`, `user@example.com`. Необязательно: перед коммитом прогонять `gitleaks` и личный список запрещённых строк, который хранится вне репозитория.

Схема «Фото» новой версии macOS не добавляется «вслепую»: без тестовой медиатеки этой версии она остаётся неподдерживаемой. Заведите issue по шаблону «новая версия macOS/Photos».

## Тесты

- `make cover` запускает тесты с `-race` и порогом покрытия 80 %.
- Сверка с эталоном: вывод `Open` сравнивается с результатами osxphotos (по UUID) на его тестовых медиатеках и на синтетической базе. Известные расхождения записаны с причинами в `testdata/golden/divergences.json`.
- Свежий osxphotos: ручной workflow `upstream-check` строит эталон последней версией с PyPI, прогоняет на нём тесты модуля и при расхождениях или если эталон не строится открывает от имени github-actions[bot] issue `osxphotos <версия>: the port differs from upstream` (или комментирует своё открытое). Порт и эталон в репозитории он не меняет: обновление идёт обычным путём, через PR.
- Схемы: границы диапазонов и щели между ними; каждая читаемая колонка есть в DDL своей схемы.
- Поля сверх osxphotos, намеренные отличия и состояния, которых нет в его медиатеках, проверяют SQL-миграции с синтетическими значениями на временной копии базы. Правила и список случаев — в [testdata/libraries/SOURCES.md](testdata/libraries/SOURCES.md).

## Тесты, меняющие «Фото»

Тесты будущего `photokit`, меняющие медиатеку (тег `photokit_live`), будут запускаться только вручную, под отдельной учётной записью macOS с отдельным Apple ID и тестовой медиатекой, никогда в CI; остальные тесты медиатеку не трогают.

## Внешние участники

- Для PR из форка CI запускается после одобрения мейнтейнера.
- PR, меняющий `.github/`, `scripts/`, `Makefile`, `.svu.yml`, `go.mod` или `go.sum`, объясните в описании: мейнтейнер проверяет, что изменение не ослабляет проверки.
- Сборка под macOS будет нужна для `photokit` (cgo); остальной код собирается и проверяется и на Linux.

## Выпуск (для мейнтейнера)

Релиз выходит сам после слияния каждого PR, менявшего `osxphotos/`. Когда CI на коммите в `main` зелёный, job `release` в `ci.yml` вычисляет версию, прогоняет `govulncheck`, публикует GitHub Release (он же создаёт тег `osxphotos/vX.Y.Z` на этом коммите) и прогревает прокси Go.

Версию не назначают, а вычисляют: [svu](https://github.com/caarlos0/svu) берёт заголовки коммитов в `main`, менявших `osxphotos/`, с последнего тега `osxphotos/vX.Y.Z`; правила — в `.svu.yml`. Следующую версию показывает `make next-version`.

| Заголовки с последнего тега | до `1.0.0` | после `1.0.0` |
|---|---|---|
| есть `type(scope)!:` | minor | major |
| иначе есть `feat(scope):` | minor | minor |
| иначе любой другой тип или заголовок вне правила | patch | patch |

PR, не менявший `osxphotos/`, релиза не выпускает. Переход на `1.0.0` из заголовков не выводится: его выпускает мейнтейнер ручным запуском `ci.yml` (Run workflow) с флагом `major`. С версии 2 путь модуля в `osxphotos/go.mod` получает суффикс `/vN`: его меняет тот же PR с `!`, автоматической проверки нет.

Заметки к релизу — те же заголовки PR с суффиксом ` (#N)` между двумя тегами, по разделам: Breaking changes, Features, Bug fixes, Documentation, Other. Они только на английском и вручную не переводятся. `CHANGELOG.md` не ведётся.

Опубликованный тег не переносится: версию модуля кеширует прокси Go. Ошибочную версию закрывает следующая вместе с директивой `retract`.
