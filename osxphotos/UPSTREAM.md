# Upstream: osxphotos

**English** | [Русский](#upstream-osxphotos-ru)

For contributors who compare behavior with Python osxphotos or update the port. Users need only the [README](README.md).

This module is a Go port of parts of [osxphotos](https://github.com/RhetTbull/osxphotos). The port follows one fixed upstream release; changes made upstream after that release are not ported until the version below is updated.

```text
Upstream version: 0.77.2
Upstream tag: v0.77.2
Tag commit: da8dfb212c19c61238dd1a9da8c87fc289324450
```

The version must equal the one in `tools/golden/requirements.txt` (the version used to generate reference data). CI fails when they differ, so moving to a new upstream version changes both files in the same pull request.

Upstream references below are written as `file:line` in that release. Paths are relative to the `osxphotos/` package of the release, as in the table.

## Intentional differences

If you only read three things: (1) models outside the supported table return `ErrUnsupportedSchema` instead of guessing; (2) the database is always read from a copy; (3) `Photos()` applies no implicit filters; `Query(query.Options{})` returns what `osxphotos query` returns.

- A model from 13000 to 16319 (Photos 5-7 and the pre-release builds 16000-16319) or from 18000 to 18200 gives `ErrUnsupportedSchema`. Upstream reads all of these with their own schemas (`_constants.py:56-62`).
- Any other model that is not in the schema table also gives `ErrUnsupportedSchema`: below 13000, 19000-19062, 20000-269999999, above 270999999, or a missing `PLModelVersion`. Upstream assumes the latest schema for a model outside all of its ranges and for a missing one (`photosdb/photosdb_utils.py:131-136`, `photosdb/photosdb_utils.py:160-163`).
- A string `PLModelVersion` is accepted only as ASCII decimal digits. Upstream `int()` also accepts a sign, surrounding spaces and non-ASCII digits (`photosdb/photosdb_utils.py:137`).
- `Z_PLIST` over 1 MiB, or a binary property list with more than 4096 objects or one whose decoding would expand beyond its size, gives `ErrUnsupportedSchema`. `SystemLibraryPath` skips a preferences file over 1 MiB or one that is not a property list. Upstream `plistlib` has no such limits (`photosdb/photosdb_utils.py:114`, `utils.py:193`).
- The database is always read from a copy that includes the `-wal` file. Upstream copies the database only when it is locked (`photosdb/photosdb.py:438-443`, `sqlite_utils.py:125-137`). A database or `-wal` that is not a regular file (a named pipe, a device, a directory) is refused before it is opened; upstream `sqlite3` opens a named pipe and blocks.
- `Info.LibraryPath` is the directory as given to `Open`, or, for a database file, the parent of its directory made absolute; upstream makes the derived path absolute and resolves symbolic links, and takes `library_path` as given (`photosdb/photosdb.py:349-350`, `photosdb/photosdb.py:452-458`). `Options.LibraryPath` must exist; upstream does not check it (`photosdb/photosdb.py:456-458`). `Info.DBPath` is absolute but its symbolic links are not resolved (`photosdb/photosdb.py:349-350`, `photosdb/photosdb.py:698-701`). A `photos.db` without `Photos.sqlite` beside it, or a library with only `database/photos.db`, gives a not-exist error; upstream reads it as a database of Photos 4 or earlier (`photosdb/photosdb.py:359-362`, `photosdb/photosdb.py:370-376`).
- `Photos()` has no implicit filters: it returns trashed photos and unselected burst frames as well. `Query` makes the selection of osxphotos `photos()`, a photo or a movie outside the trash that is not an unselected burst frame (one whose pick type is not 0 and has neither the selected nor the key bit), as `PhotosDB.query` does (`photosdb/photosdb.py:3269-3276`, `photosdb/photosdb.py:3346-3353`, `photosdb/photosdb.py:3355-3358`, `photoquery.py:426-445`).
- `PhotosWith` with `Albums` looks for the titles among user albums only; upstream looks among every album of that title, of any kind, such as shared albums and projects (`photosdb/photosdb.py:1904-1943`, `photosdb/photosdb.py:2629-2635`, `photosdb/photosdb.py:3283-3298`). An album without a title matches the title `""`; upstream keys it by `None`. Its result is in the order of `query.Sort`; upstream's is that of a set.
- `query.Options` ports `QueryOptions` field by field (`photoquery.py:147-241`). Not ported: `exif` (exiftool), `label` (the search index), `place` and `no_place` (reverse geolocation), `query_eval` (Python expressions), `regex` (templates), `selected` (the selection in the Photos app, through AppleScript).
- `query.Apply` has no comments and likes: with `HasComment` or `HasLikes` it selects nothing and with `NoComment` or `NoLikes` everything; `DB.Query` passes them through `query.Catalog`, as `photo_query` reads them from the photo (`photoquery.py:656-664`).
- A `DateAdded` that the database does not have is 1970-01-01T00:00:00Z for `AddedAfter`, `AddedBefore` and `AddedInLast`; upstream takes midnight of 1970-01-01 in the time zone of the computer (`photos_datetime.py:19-21`, `photoquery.py:822-837`).
- `Datetime` of a `CommentInfo` or a `LikeInfo` without a date in the database, or with one outside the years 1-9999, is nil; upstream gives midnight of 1970-01-01 in the time zone of the computer, the value by which `DB.Comments` and `DB.Likes` sort it (`photos_datetime.py:19-21`, `photos_datetime.py:70-89`, `photosdb/_photosdb_process_comments.py:130`, `photosdb/_photosdb_process_comments.py:146-150`).
- The first `Function` gets the photos in catalog (UUID) order; in upstream the order depends on which filters ran, some of them pass through a set (`photoquery.py:859-861`); with `Duplicate`, the order of the duplicate step, as upstream (`photoquery.py:754-765`).
- A photo that matches several values of `Title` or `Description` is returned once; upstream returns it once per value (`photoquery.py:480-516`).
- `IgnoreCase` folds case with `strings.ToLower`; Python `str.lower` gives another result for a few characters, such as U+0130 (`photoquery.py:484-491`).
- `query.Duplicates`, `DB.Duplicates` and `Duplicate` compare `OriginalFilesize`, `Height`, `Width` and `UTI` as the module reads them: a `NULL` column is 0 or `""` and matches 0 or `""`, where upstream compares `None`, which matches only `None`; dates are compared to the nanosecond, upstream compares Python datetimes to the microsecond (`photosdb/photosdb.py:3411-3420`).
- `Persons()` and `PersonCounts()` count the faces on the photos that `Photos()` returns; upstream counts the faces of every asset, those without a `ZADDITIONALASSETATTRIBUTES` row included, and keeps the order of a set and of the count (`photosdb/photosdb.py:498-509`, `photosdb/photosdb.py:553-557`).
- `NULL` in the pick type of a burst frame is 0. Upstream fails on `None & int` (`photosdb/photosdb.py:3347-3351`).
- `BurstPhotos` is in UUID order, and `BurstKeyPhoto` of a burst with several key photos is the first of them by UUID; upstream iterates a set (`photoinfo.py:1009-1044`).
- `IsMissing`: the first pass over the resources of subtypes 1 and 3 of the asset lets the highest `Z_PK` decide, where upstream takes the last row read (`photosdb/photosdb.py:2449-2495`). The second pass runs the query of upstream as it is, the resources of any asset with the fingerprint, and the last row read decides as in upstream (`photosdb/photosdb.py:2498-2516`): with no index on `ZFINGERPRINT` that row depends on the plan of SQLite, and only the same query gives the same row.
- `Date` is in the zone of `TZName` when it is an IANA name or an abbreviation of `TZ_OVERRIDES` whose zone has the offset `TZOffset` at the moment of the photo, and in the fixed zone of `TZOffset` otherwise; a `GMT±HHMM` name equal to `TZOffset` gives a zone with that offset upstream too. A zone name that is not a normalized path, such as `./Europe/Paris`, is not a zone, as for upstream `zoneinfo`. Upstream checks the offset of the zone at the naive time of the photo in the time zone of the computer, and for other names searches every zone of the system; the zone it finds has the offset of `TZOffset`, so the clock time differs only next to a daylight saving change (`photos_datetime.py:50-65`, `tzcanonical.py:380-446`). Time zone data come from the system and, where it has none, from `time/tzdata`, as upstream does with the `tzdata` package.
- Paths are looked up only inside the library: a symbolic link is never a file, and a link in a directory of the path is followed only while it stays inside the library. An absolute `ZDIRECTORY` (a referenced file) or an empty one gives the path ""; upstream uses an absolute one as is and looks for an empty one in `originals/<file name>`. Referenced files have no `PathLive` and `PathRaw`. Photos of shared albums and "Shared with you" photos not saved to the library have `Path` and `PathLive` ""; their `PathRaw` is looked up in `originals/`, as upstream does. The shared moment directory is not searched: a photo of a shared moment has a `Path` only when its file is in `originals/` (`photoinfo.py:209-234`, `photoinfo.py:545-571`, `photoinfo.py:1063-1071`). With several candidate RAW files the first in name order is used; upstream takes the first of `os.listdir`, whose order is unspecified (`utils.py:364-389`, `photoinfo.py:554-555`).
- `PathEdited`, `PathEditedLive`, `AdjustmentsPath`, `OriginalAdjustmentsPath` and `PathDerivatives` hold a file only when it is a regular file inside the library; a `ZUUID` with `/` gives them all "", where upstream builds the path from it as is. Upstream follows symbolic links, and `path_exists` accepts a directory too (`photoinfo.py:336-341`, `photoinfo.py:761-762`, `photoinfo.py:779-780`, `photoinfo.py:1218`, `utils.py:573-587`, `utils.py:772-773`); a derivatives directory that cannot be read gives no previews, where upstream raises `PermissionError` (`utils.py:762`). Previews of equal size are in name order; upstream keeps the order of `os.listdir` (`utils.py:762-778`).
- `Adjustments` and `OriginalAdjustments` read the file on every call; upstream caches it (`photoinfo.py:783-800`). A file that is no longer a regular file inside the library gives nil, as upstream gives `None` when `is_file()` fails (`photoinfo.py:761-762`, `photoinfo.py:789-791`); a file that cannot be read gives nil, where upstream raises (`adjustmentsinfo.py:126`); a root that is not a dictionary gives zero values, where upstream raises `AttributeError` (`adjustmentsinfo.py:39`). A file over 1 MiB, or a binary property list refused as `Z_PLIST` is (above), gives a nil `Plist` (upstream: an empty dictionary); `adjustmentData` that inflates past 1 MiB, or is a binary property list refused so, is not decoded (`adjustmentsinfo.py:77-113`); its JSON numbers are float64, where upstream `json` gives int for an integer, so `Orientation` of an edit made in Photos is float64(1), not 1. Values of another type give `""` or nil, where upstream returns them as they are; a string `adjustmentData` gives `Data` as its UTF-8 bytes.
- `Orientation` of an edited asset is the database column. Upstream reads it from the property list of the edit (`photoinfo.py:1396-1404`).
- The UTI of an extension comes only from the table of `uti.py`, without `mdls` (`uti.py:642-653`), and the preferred extension of a UTI only from the same table, without CoreServices (`uti.py:594-610`).
- `export` ports only the file names of `PhotoExporter._export` (`photoexporter.py:297-303, 371, 392, 413-471, 476-500, 554-565, 1923-1929`) and `increment_filename_with_count` (`utils.py:399-437`); exporting files, the export database, sidecars, exiftool and the AppleScript fallback are not ported. `Names` builds the companions from the name it is given, as upstream builds them from the numbered `dest` (308); `IncrementName` takes the stems of the directory from the caller as `StemKey` values, compared in NFC and lower case where upstream compares the NFD form (`utils.py:428, 431-433`). The stem of a name is in NFC; upstream normalizes the incremented name and the AAE names to NFD on macOS (`unicode.py:18`, `utils.py:431, 437`, `photoexporter.py:479, 1927-1929`), which APFS treats as the same name. Case is folded with `strings.ToLower`; Python `str.lower` gives another result for a few characters, such as U+0130 and a final Σ (`utils.py:428, 433`).
- A repeated or missing `ZUUID` of an asset with a `ZADDITIONALASSETATTRIBUTES` row is an error of `Open`; assets without that row are left out unchecked, as upstream drops them (`photosdb/photosdb.py:2086-2090`). Upstream keeps the last row (`photosdb/photosdb.py:2356`). The album memberships of such assets are left out too, while upstream finds the photo of a membership row by its `ZUUID` (`photosdb/photosdb.py:1873-1901`, `photosdb/photosdb.py:3378-3394`).
- A chain of `ZPARENTFOLDER` of an album or a folder that does not reach the root folder or a row without a parent (a missing parent or a cycle) is an error of `Open`; a parent row without `ZUUID`, or of a `ZKIND` other than 2, 1505, 1506, 1508, 3999 and 4000, counts as missing. Upstream fails on a missing parent of any row (`photosdb/photosdb.py:1977-1980`) and on a cycle above an album (`photosdb/photosdb.py:2944-2965`), and accepts a cycle of folders that holds no album.
- An empty or repeated `ZUUID` among the rows of `ZGENERICALBUM` of `ZKIND` 2, 1505, 1506, 1508, 3999 and 4000 is an error of `Open`; upstream keeps the last row in a dictionary by `ZUUID` (`photosdb/photosdb.py:1923-1948`).
- `FolderInfo()`, `FolderTitles()` and the `Subfolders` and `Albums` of a folder are in UUID order; upstream keeps the order in which SQLite returns the rows of `ZGENERICALBUM` (`photosdb/photosdb.py:570-610`, `albuminfo.py:421-491`).
- `LibraryListOrder` of a folder in the trash, and of the folders and albums in it, starts with the orders of its enclosing folders. Upstream drops them when the enclosing folder holds no folder or album outside the trash, as an empty `FolderInfo` is false (`albuminfo.py:508-511`, `albuminfo.py:525-527`).
- A `TZOffset` outside (-86400, 86400) seconds gives `Date` 1970-01-01T00:00:00Z when `TZName` gives no zone (see `Date` above). Upstream gives the same date (`ValueError`), but for an offset outside the range of `timedelta` it fails with an uncaught `OverflowError` (`photos_datetime.py:64-67`).
- An empty GUID string means no GUID, as `NULL` does.
- `AlbumUUIDs` includes albums in the trash; `AlbumInfoOf`, `AlbumTitlesOf`, `BurstAlbumInfoOf` and `BurstAlbumTitlesOf` leave them out, as osxphotos `album_info`, `albums`, `burst_album_info` and `burst_albums` of a photo do (`photoinfo.py:633-671`, `photoinfo.py:2029-2034`).
- `AlbumInfo()` returns every album of `ZKIND` 2 outside the trash. Upstream `album_info` also requires an empty `ZCLOUDOWNERHASHEDPERSONID` (`photosdb/photosdb.py:3206`); no album of `ZKIND` 2 in the test libraries has one.
- `ImportInfo()` returns every import session of `ZKIND` 1506 outside the trash, in UUID order; upstream also requires an empty `ZCLOUDOWNERHASHEDPERSONID` and keeps the order of the rows of `ZGENERICALBUM` (`photosdb/photosdb.py:3197-3210`). `Import` finds only import sessions; upstream `ImportInfo(db, uuid)` takes a row of any kind, and `import_info` of a photo is the row of `ZASSET.ZIMPORTSESSION` whatever its kind (`albuminfo.py:303-309`, `photosdb/photosdb.py:2383-2402`). No row of `ZKIND` 1506 in the test libraries has an owner, and no asset points to a row of another kind.
- `ProjectInfo()` returns every project of `ZKIND` 1508 outside the trash, in UUID order; upstream also requires an empty `ZCLOUDOWNERHASHEDPERSONID` and keeps the order of the rows of `ZGENERICALBUM` (`photosdb/photosdb.py:3187-3210`). `Project` finds only projects; upstream `ProjectInfo(db, uuid)` takes a row of any kind (`albuminfo.py:368`). No project of the test libraries has an owner.
- `ProjectInfoOf` sorts by title, then by UUID, a project once; a project without a title comes first. Upstream keeps the order and the repeats of the membership rows among equal titles, and fails when it compares a title that is `None` with another (`photoinfo.py:696-703`, `photosdb/photosdb.py:1888-1901`).
- The parent of a project and of a shared album is its `ZPARENTFOLDER` row of any `ZKIND`, as upstream; a parent row without `ZUUID` is an error of `Open`; upstream builds a `FolderInfo` without a UUID there (`albuminfo.py:229-234`, `photosdb/photosdb.py:1923-1948`).
- `PhotoUUIDs` of an import session without photos is nil; upstream `ImportInfo.photos` raises `ValueError` there, unpacking an empty `zip` (`albuminfo.py:331-338`).
- `AlbumInfo()` and `SharedAlbumInfo()` are in UUID order, `AlbumTitles()`, `SharedAlbumTitles()` and `AlbumTitlesOf` are sorted, `AlbumInfoOf` sorts by title, then by UUID. Upstream keeps the order of the rows of `ZGENERICALBUM`, of a Python set and of the membership rows (`photosdb/photosdb.py:612-667`, `photosdb/photosdb.py:3212-3225`, `photoinfo.py:655-662`).
- `albuminfo.AlbumInfo.Owner` (osxphotos `owner`) is the full name of `ZCLOUDOWNERHASHEDPERSONID` among the invitees of `ZCLOUDSHAREDALBUMINVITATIONRECORD` and the owners of `ZGENERICALBUM` that have a first or a last name, as upstream (`_photosdb_process_comments.py:52-89`, `albuminfo.py:113-133`); the order of the `UNION` is fixed by `ORDER BY`, as SQLite returns it. For an ID that the `UNION` does not hold, the name is the given and family name of a `ZSHAREPARTICIPANT.ZNAMECOMPONENTS` archive of that ID (`_photosdb_process_comments.py:155-187`); the archives of one ID are tried in `Z_PK` order, the order of the table scan of the `SELECT DISTINCT` of upstream, which leaves the order to SQLite; the classes that upstream maps (`shareparticipant.py:120-127`) are not checked; an archive over 1 MiB, or a binary property list refused as `Z_PLIST` is (above), gives no name, where upstream decodes it. Import sessions have no owner here; upstream gives one to an import session too (`albuminfo.py:113-143`); no import session of the test libraries has one.
- `photoinfo.PhotoInfo.Owner` is "" for a photo without an owner or with an owner without a name; upstream `owner` is `None` (`photoinfo.py:1441-1459`). It is resolved when the library is read, like `AlbumInfo.Owner`.
- `photoinfo.PhotoInfo.ExifInfo` (osxphotos `exif_info`) is read once in `Open`. A string that the row does not have, or a photo without a row, is ""; upstream has `None` (`exifinfo.py:42-77`). - Shared albums of Photos 11 and later, the `CollectionShare` records of `ZSHARE`, are read as upstream reads them (`photosdb/photosdb.py:1950-1956`, `photosdb/photosdb.py:2787-2942`), except: a record without `ZUUID` and its photos are left out; an empty `ZUUID`, or one that another record or a row of `ZGENERICALBUM` also has, is an error of `Open`, where upstream keeps the last in one dictionary; a value that cannot be read fails `Open`, and a `ZSHAREPARTICIPANT` without `ZHASHEDPERSONID` gives no owner, where upstream logs a warning and goes on without the shared albums (`photosdb/photosdb.py:1953-1956`); of several participants with the owner role the one with the highest `Z_PK` is the owner, and of several resources of subtype 8 of a video the one with the highest `Z_PK` decides `IsMissing`, where upstream takes the last row read (`photosdb/photosdb.py:2850-2861`, `photosdb/photosdb.py:2927-2942`). A keyword without a title is `""` in all three; upstream has `None` (`unicode.py:79-80`, `photosdb/photosdb.py:2006-2014`).

- `AlbumCounts` and `SharedAlbumCounts` count the photos of each album that `Photos()` returns, and an empty album adds 0. - `PhotoUUIDs` of an album is a set; `AlbumPhotos` gives the photos in the order of the album. A `NULL` position of a photo in an album comes before the numbers; upstream fails when an album has both (`albuminfo.py:37-53`, `albuminfo.py:165-187`). `PhotoIndex` of a photo not in the album returns -1, false; upstream raises `ValueError` (`albuminfo.py:280-287`).

- `DB.SharedMomentInfo` and `DB.ShareInfo` (osxphotos `shared_moment_info` and `share_info`) come from the rows of `ZSHARE` read once in `Open`; upstream runs its query on every access (`shareinfo.py:129-148`, `photoinfo.py:1606-1626`), so a value of an unexpected type in `ZSHARE` fails `Open` here and only that property upstream. A date of 0 in `ShareInfo` is nil; upstream leaves the number 0 there (`shareinfo.py:74-75`). `DB.ShareInfo` follows `ZASSET.ZLIBRARYSCOPE`, a key that upstream itself calls a guess, ported as is (`shareinfo.py:156-165`). A name part that the archive does not have, or that is not a string, is `""`; upstream keeps `None` or the value, and `share_participants` prints `None` as `None`. The raw archive (`_name_components`) is not kept.

- `template.Parse` reports a syntax error with the byte offset and the expected symbol; upstream raises `ValueError` with the message of TextX (`phototemplate.py:504-507`). A template nested deeper than 32 statements is a syntax error; upstream is bounded only by the recursion limit of Python.
- `Render` reads the fields of a photo through `template.Photo`. A field that upstream has but the implementation does not give, and `{exiftool}`, `{function}`, `{detected_text}` and `{osxphotos_cmd_line}`, which call programs or code, give an error that wraps `ErrUnsupportedField`; upstream renders the value or `None` (`phototemplate.py:839-884`). A name that upstream does not have goes to `unmatched`, as upstream (881-883). A render of more than `RenderOptions.MaxResults` strings (10 000 by default) is `ErrTooManyValues`; upstream is not bounded (774-783). An empty `NoneStr`, `InplaceSep` or `PathSep` means the default of upstream (`_`, `,`, `/`): the zero value of `RenderOptions` is `RenderOptions()` of upstream (388-400).

## Upstream: osxphotos (по-русски)

Для тех, кто сравнивает поведение с Python osxphotos или обновляет порт; пользователю достаточно [README](README.md).

Модуль — порт частей [osxphotos](https://github.com/RhetTbull/osxphotos) на Go. Порт следует одному зафиксированному выпуску upstream; правки upstream после этого выпуска не переносятся, пока версия выше не обновлена.

### Намеренные отличия

Если читать только три пункта: (1) модели вне таблицы поддерживаемых дают `ErrUnsupportedSchema`, а не догадку; (2) база всегда читается из копии; (3) `Photos()` без неявных фильтров; `Query(query.Options{})` отдаёт то же, что `osxphotos query`.

- Номер модели от 13000 до 16319 (Photos 5-7 и предварительные сборки 16000-16319) или от 18000 до 18200 даёт `ErrUnsupportedSchema`. Upstream читает все эти модели по их собственным схемам (`_constants.py:56-62`).
- Любой другой номер модели, которого нет в таблице схем, тоже даёт `ErrUnsupportedSchema`: меньше 13000, 19000-19062, 20000-269999999, больше 270999999 или отсутствующий `PLModelVersion`. Upstream для номера вне всех своих диапазонов и для отсутствующего берёт последнюю схему (`photosdb/photosdb_utils.py:131-136`, `photosdb/photosdb_utils.py:160-163`).
- Строковый `PLModelVersion` принимается, только если это десятичные цифры ASCII. `int()` в upstream принимает ещё знак, пробелы по краям и цифры других алфавитов (не ASCII) (`photosdb/photosdb_utils.py:137`).
- `Z_PLIST` больше 1 МиБ или двоичный список свойств, в котором больше 4096 объектов или который при разборе разрастается больше своего размера, даёт `ErrUnsupportedSchema`. `SystemLibraryPath` пропускает файл настроек больше 1 МиБ или не являющийся списком свойств. В `plistlib` upstream таких ограничений нет (`photosdb/photosdb_utils.py:114`, `utils.py:193`).
- База всегда читается из копии вместе с файлом `-wal`. Upstream копирует базу, только когда она заблокирована (`photosdb/photosdb.py:438-443`, `sqlite_utils.py:125-137`). База или `-wal`, которые не обычный файл (именованный канал, устройство, каталог), отклоняются до открытия; `sqlite3` в upstream открывает именованный канал и зависает.
- `Info.LibraryPath` — каталог, как передан в `Open`, а для файла базы — родитель её каталога, путь абсолютный; upstream делает выведенный путь абсолютным и разрешает символические ссылки, а `library_path` берёт как передан (`photosdb/photosdb.py:349-350`, `photosdb/photosdb.py:452-458`). `Options.LibraryPath` должен существовать; upstream его не проверяет (`photosdb/photosdb.py:456-458`). `Info.DBPath` абсолютный, но символические ссылки в нём не разрешаются (`photosdb/photosdb.py:349-350`, `photosdb/photosdb.py:698-701`). `photos.db` без `Photos.sqlite` рядом или медиатека, где есть только `database/photos.db`, дают ошибку «не существует»; upstream читает такой файл как базу Photos 4 и раньше (`photosdb/photosdb.py:359-362`, `photosdb/photosdb.py:370-376`).
- `Photos()` без неявных фильтров: возвращает и фото из корзины, и невыбранные кадры серий. Выборку `photos()` из osxphotos — фото или видео вне корзины, кроме невыбранных кадров серий (у такого кадра отметка не 0 и в ней нет ни бита выбранного, ни бита ключевого кадра), — делает `Query`, как `PhotosDB.query` (`photosdb/photosdb.py:3269-3276`, `photosdb/photosdb.py:3346-3353`, `photosdb/photosdb.py:3355-3358`, `photoquery.py:426-445`).
- `PhotosWith` с `Albums` ищет названия только среди пользовательских альбомов; upstream — среди всех альбомов с этим названием любого вида, например общих альбомов и проектов (`photosdb/photosdb.py:1904-1943`, `photosdb/photosdb.py:2629-2635`, `photosdb/photosdb.py:3283-3298`). Альбом без названия совпадает с названием `""`; upstream хранит его под `None`. Результат — в порядке `query.Sort`; у upstream — в порядке множества.
- `query.Options` переносит `QueryOptions` поле за полем (`photoquery.py:147-241`). Не переносятся: `exif` (exiftool), `label` (индекс поиска), `place` и `no_place` (обратное геокодирование), `query_eval` (выражения Python), `regex` (шаблоны), `selected` (выделение в приложении «Фото» через AppleScript).
- У `query.Apply` нет комментариев и отметок: с `HasComment` или `HasLikes` он не выбирает ничего, с `NoComment` или `NoLikes` — всё; `DB.Query` передаёт их через `query.Catalog`, как `photo_query` читает их у фото (`photoquery.py:656-664`).
- `DateAdded`, которого нет в базе, для `AddedAfter`, `AddedBefore` и `AddedInLast` — 1970-01-01T00:00:00Z; upstream берёт полночь 1970-01-01 в поясе компьютера (`photos_datetime.py:19-21`, `photoquery.py:822-837`).
- `Datetime` у `CommentInfo` или `LikeInfo`, у которых в базе нет даты или она вне 1-9999 годов, — nil; upstream даёт полночь 1970-01-01 в поясе компьютера, и по этому значению их сортируют `DB.Comments` и `DB.Likes` (`photos_datetime.py:19-21`, `photos_datetime.py:70-89`, `photosdb/_photosdb_process_comments.py:130`, `photosdb/_photosdb_process_comments.py:146-150`).
- Первая `Function` получает фото в порядке каталога (по UUID); в upstream порядок зависит от того, какие фильтры сработали, часть из них проходит через множество (`photoquery.py:859-861`); с `Duplicate` — в порядке шага дубликатов, как в upstream (`photoquery.py:754-765`).
- Фото, которое подходит под несколько значений `Title` или `Description`, возвращается один раз; upstream возвращает его по разу на значение (`photoquery.py:480-516`).
- `IgnoreCase` сравнивает без учёта регистра через `strings.ToLower`; `str.lower` в Python для нескольких символов даёт другой результат, например для U+0130 (`photoquery.py:484-491`).
- `query.Duplicates`, `DB.Duplicates` и `Duplicate` сравнивают `OriginalFilesize`, `Height`, `Width` и `UTI` в том виде, в каком их читает модуль: колонка `NULL` даёт 0 или `""` и совпадает с 0 или `""`, а upstream сравнивает `None`, которое совпадает только с `None`; даты сравниваются до наносекунды, upstream сравнивает datetime Python до микросекунды (`photosdb/photosdb.py:3411-3420`).
- `Persons()` и `PersonCounts()` считают лица на фото, которые отдаёт `Photos()`; upstream считает лица всех объектов, включая объекты без строки `ZADDITIONALASSETATTRIBUTES`, и сохраняет порядок множества и счёта (`photosdb/photosdb.py:498-509`, `photosdb/photosdb.py:553-557`).
- `NULL` в отметке кадра серии — 0. Upstream падает на `None & int` (`photosdb/photosdb.py:3347-3351`).
- `BurstPhotos` идёт по UUID, а `BurstKeyPhoto` серии с несколькими ключевыми кадрами — первый из них по UUID; upstream обходит множество (`photoinfo.py:1009-1044`).
- `IsMissing`: в первом проходе по ресурсам подтипов 1 и 3 самого объекта решает наибольший `Z_PK`, а upstream берёт последнюю прочитанную строку (`photosdb/photosdb.py:2449-2495`). Второй проход выполняет запрос upstream как есть — ресурсы любого объекта с тем же отпечатком, — и решает последняя прочитанная строка, как в upstream (`photosdb/photosdb.py:2498-2516`): индекса по `ZFINGERPRINT` нет, эта строка зависит от плана SQLite, и ту же строку даёт только тот же запрос.
- `Date` — в зоне `TZName`, если это имя IANA или сокращение из `TZ_OVERRIDES`, у зоны которого в момент снимка смещение `TZOffset`; иначе — в фиксированной зоне `TZOffset`; имя `GMT±HHMM`, равное `TZOffset`, и у upstream даёт зону с этим смещением. Имя пояса, которое не является нормализованным путём, например `./Europe/Paris`, — не пояс, как и у `zoneinfo` upstream. Upstream сверяет смещение зоны в «наивном» времени снимка в поясе компьютера, а для других имён перебирает все пояса системы; найденная зона имеет смещение `TZOffset`, поэтому время на часах расходится только рядом с переходом на летнее время (`photos_datetime.py:50-65`, `tzcanonical.py:380-446`). Данные поясов — из системы, а где их там нет — из `time/tzdata`, как у upstream с пакетом `tzdata`.
- Пути ищутся только внутри медиатеки: символическая ссылка — никогда не файл, а ссылка в каталоге пути проходится, только пока остаётся внутри медиатеки. Абсолютный `ZDIRECTORY` (файл-ссылка) или пустой даёт путь ""; upstream берёт абсолютный как есть, а пустой ищет в `originals/<имя файла>`. У файлов-ссылок нет `PathLive` и `PathRaw`. У фото общих альбомов и фото «Отправлено вам», не сохранённых в медиатеку, `Path` и `PathLive` — ""; их `PathRaw` ищется в `originals/`, как в upstream. Каталог общих моментов не просматривается: у фото общего момента `Path` есть, только если его файл лежит в `originals/` (`photoinfo.py:209-234`, `photoinfo.py:545-571`, `photoinfo.py:1063-1071`). Из нескольких файлов-кандидатов RAW берётся первый по порядку имён; upstream берёт первый из `os.listdir`, порядок которого не задан (`utils.py:364-389`, `photoinfo.py:554-555`).
- `PathEdited`, `PathEditedLive`, `AdjustmentsPath`, `OriginalAdjustmentsPath` и `PathDerivatives` содержат файл, только если это обычный файл внутри медиатеки; при `ZUUID` с `/` все они "", а upstream строит путь из него как есть. Upstream проходит по символическим ссылкам, а `path_exists` принимает и каталог (`photoinfo.py:336-341`, `photoinfo.py:761-762`, `photoinfo.py:779-780`, `photoinfo.py:1218`, `utils.py:573-587`, `utils.py:772-773`); каталог превью, который нельзя прочитать, не даёт превью, а upstream выбрасывает `PermissionError` (`utils.py:762`). Превью одного размера идут по порядку имён; upstream сохраняет порядок `os.listdir` (`utils.py:762-778`).
- `Adjustments` и `OriginalAdjustments` читают файл при каждом вызове; upstream его кеширует (`photoinfo.py:783-800`). Файл, который уже не обычный файл внутри медиатеки, даёт nil, как `None` у upstream при неудаче `is_file()` (`photoinfo.py:761-762`, `photoinfo.py:789-791`); файл, который не читается, даёт nil, а upstream выбрасывает исключение (`adjustmentsinfo.py:126`); корень, который не словарь, даёт нулевые значения, а upstream выбрасывает `AttributeError` (`adjustmentsinfo.py:39`). Файл больше 1 МиБ или двоичный список свойств, который отклоняется, как `Z_PLIST` (выше), даёт nil `Plist` (у upstream — пустой словарь); `adjustmentData`, которое распаковывается больше чем в 1 МиБ или является так же отклонённым двоичным списком свойств, не разбирается (`adjustmentsinfo.py:77-113`); числа его JSON — float64, а upstream `json` даёт int для целого, поэтому `Orientation` правки из «Фото» — float64(1), а не 1. Значения другого типа дают `""` или nil, а upstream возвращает их как есть; строковое `adjustmentData` даёт `Data` — его байты UTF-8.
- `Orientation` правленого объекта — колонка базы. Upstream читает её из списка свойств правки (`photoinfo.py:1396-1404`).
- UTI по расширению берётся только из таблицы `uti.py`, без `mdls` (`uti.py:642-653`), а предпочитаемое расширение UTI — только из той же таблицы, без CoreServices (`uti.py:594-610`).
- `export` переносит только имена файлов `PhotoExporter._export` (`photoexporter.py:297-303, 371, 392, 413-471, 476-500, 554-565, 1923-1929`) и `increment_filename_with_count` (`utils.py:399-437`); экспорт файлов, база экспорта, сайдкары, exiftool и запасной путь через AppleScript не переносятся. `Names` строит спутников от переданного имени, как upstream — от нумерованного `dest` (308); `IncrementName` получает основы имён каталога от вызывающего как значения `StemKey`, сравнение — в NFC и строчных там, где upstream сравнивает форму NFD (`utils.py:428, 431-433`). Основа имени — в NFC; upstream на macOS приводит нумерованное имя и имена AAE к NFD (`unicode.py:18`, `utils.py:431, 437`, `photoexporter.py:479, 1927-1929`), для APFS это одно имя. Регистр сворачивается через `strings.ToLower`; `str.lower` в Python для нескольких символов даёт другой результат, например для U+0130 и конечной Σ (`utils.py:428, 433`).
- Повтор или отсутствие `ZUUID` у объекта со строкой `ZADDITIONALASSETATTRIBUTES` — ошибка `Open`; объекты без этой строки отбрасываются без проверки, как в upstream (`photosdb/photosdb.py:2086-2090`). Upstream оставляет последнюю строку (`photosdb/photosdb.py:2356`). Членство таких объектов в альбомах тоже отбрасывается, а upstream находит фото строки членства по её `ZUUID` (`photosdb/photosdb.py:1873-1901`, `photosdb/photosdb.py:3378-3394`).
- Цепочка `ZPARENTFOLDER` альбома или папки, которая не доходит до корневой папки или до строки без родителя (родителя нет или цикл), — ошибка `Open`; родительская строка без `ZUUID` или с `ZKIND`, отличным от 2, 1505, 1506, 1508, 3999 и 4000, считается отсутствующей. Upstream падает на отсутствующем родителе любой строки (`photosdb/photosdb.py:1977-1980`) и на цикле над альбомом (`photosdb/photosdb.py:2944-2965`), а цикл папок без альбомов принимает.
- Пустой или повторённый `ZUUID` среди строк `ZGENERICALBUM` с `ZKIND` 2, 1505, 1506, 1508, 3999 и 4000 — ошибка `Open`; upstream оставляет последнюю строку в словаре по `ZUUID` (`photosdb/photosdb.py:1923-1948`).
- `FolderInfo()`, `FolderTitles()`, а также `Subfolders` и `Albums` папки идут по UUID; upstream сохраняет порядок, в котором SQLite отдаёт строки `ZGENERICALBUM` (`photosdb/photosdb.py:570-610`, `albuminfo.py:421-491`).
- `LibraryListOrder` папки в корзине и вложенных в неё папок и альбомов начинается с порядков объемлющих папок. Upstream их отбрасывает, если в объемлющей папке нет папок и альбомов вне корзины: пустой `FolderInfo` ложен (`albuminfo.py:508-511`, `albuminfo.py:525-527`).
- `TZOffset` вне диапазона (-86400, 86400) секунд даёт `Date` 1970-01-01T00:00:00Z, если `TZName` не даёт зону (см. `Date` выше). Upstream даёт ту же дату (`ValueError`), но на смещении вне диапазона `timedelta` падает с непойманным `OverflowError` (`photos_datetime.py:64-67`).
- Пустая строка GUID означает отсутствие GUID, как и `NULL`.
- `AlbumUUIDs` включает альбомы в корзине; `AlbumInfoOf`, `AlbumTitlesOf`, `BurstAlbumInfoOf` и `BurstAlbumTitlesOf` их не берут, как `album_info`, `albums`, `burst_album_info` и `burst_albums` фото в osxphotos (`photoinfo.py:633-671`, `photoinfo.py:2029-2034`).
- `AlbumInfo()` возвращает все альбомы с `ZKIND` 2 вне корзины. `album_info` в upstream требует ещё пустого `ZCLOUDOWNERHASHEDPERSONID` (`photosdb/photosdb.py:3206`); ни у одного альбома с `ZKIND` 2 в тестовых медиатеках его нет.
- `ImportInfo()` возвращает все сессии импорта с `ZKIND` 1506 вне корзины, по UUID; upstream требует ещё пустого `ZCLOUDOWNERHASHEDPERSONID` и сохраняет порядок строк `ZGENERICALBUM` (`photosdb/photosdb.py:3197-3210`). `Import` находит только сессии импорта; `ImportInfo(db, uuid)` в upstream принимает строку любого вида, а `import_info` фото — строка `ZASSET.ZIMPORTSESSION` любого вида (`albuminfo.py:303-309`, `photosdb/photosdb.py:2383-2402`). Ни у одной строки с `ZKIND` 1506 в тестовых медиатеках нет владельца, и ни один объект не ссылается на строку другого вида.
- `ProjectInfo()` возвращает все проекты с `ZKIND` 1508 вне корзины, по UUID; upstream требует ещё пустого `ZCLOUDOWNERHASHEDPERSONID` и сохраняет порядок строк `ZGENERICALBUM` (`photosdb/photosdb.py:3187-3210`). `Project` находит только проекты; `ProjectInfo(db, uuid)` в upstream принимает строку любого вида (`albuminfo.py:368`). Ни у одного проекта в тестовых медиатеках нет владельца.
- `ProjectInfoOf` сортирует по названию, затем по UUID, и называет проект один раз; проект без названия идёт первым. Upstream среди одинаковых названий сохраняет порядок и повторы строк членства, а падает, когда сравнивает название `None` с другим (`photoinfo.py:696-703`, `photosdb/photosdb.py:1888-1901`).
- Родитель проекта и общего альбома — его строка `ZPARENTFOLDER` любого `ZKIND`, как в upstream; родительская строка без `ZUUID` — ошибка `Open`; upstream строит там `FolderInfo` без UUID (`albuminfo.py:229-234`, `photosdb/photosdb.py:1923-1948`).
- `PhotoUUIDs` сессии импорта без фото — nil; `ImportInfo.photos` в upstream тогда бросает `ValueError`: распаковка пустого `zip` (`albuminfo.py:331-338`).
- `AlbumInfo()` и `SharedAlbumInfo()` идут по UUID, `AlbumTitles()`, `SharedAlbumTitles()` и `AlbumTitlesOf` отсортированы, `AlbumInfoOf` сортирует по названию, затем по UUID. Upstream сохраняет порядок строк `ZGENERICALBUM`, множества Python и строк членства (`photosdb/photosdb.py:612-667`, `photosdb/photosdb.py:3212-3225`, `photoinfo.py:655-662`).
- `albuminfo.AlbumInfo.Owner` (`owner` в osxphotos) — полное имя `ZCLOUDOWNERHASHEDPERSONID` среди приглашённых `ZCLOUDSHAREDALBUMINVITATIONRECORD` и владельцев `ZGENERICALBUM`, у которых есть имя или фамилия, как в upstream (`_photosdb_process_comments.py:52-89`, `albuminfo.py:113-133`); порядок `UNION` закреплён `ORDER BY` — тот, в котором его отдаёт SQLite. Для ID, которого нет в `UNION`, имя — имя и фамилия из архива `ZSHAREPARTICIPANT.ZNAMECOMPONENTS` этого ID (`_photosdb_process_comments.py:155-187`); архивы одного ID перебираются по `Z_PK` — в порядке просмотра таблицы для `SELECT DISTINCT` upstream, который оставляет порядок SQLite; классы, которые сопоставляет upstream (`shareparticipant.py:120-127`), не проверяются; архив больше 1 МиБ или двоичный список свойств, который отклоняется, как `Z_PLIST` (выше), не даёт имени, а upstream его разбирает. У сессий импорта здесь нет владельца; upstream даёт его и сессии импорта (`albuminfo.py:113-143`); ни у одной сессии импорта в тестовых медиатеках его нет.
- `photoinfo.PhotoInfo.Owner` — "" у фото без владельца или с владельцем без имени; `owner` в upstream — `None` (`photoinfo.py:1441-1459`). Имя разрешается при чтении медиатеки, как `AlbumInfo.Owner`.
- `photoinfo.PhotoInfo.ExifInfo` (`exif_info` в osxphotos) читается один раз в `Open`. Строка, которой нет в записи, или фото без записи — ""; у upstream — `None` (`exifinfo.py:42-77`). Из двух строк `ZEXTENDEDATTRIBUTES` одного фото решает строка с наибольшим `Z_PK`; upstream оставляет последнюю прочитанную и пишет предупреждение (`photosdb/_photosdb_process_exif.py:56-61`).
- Общие альбомы «Фото» 11 и новее — записи `CollectionShare` в `ZSHARE` — читаются как в upstream (`photosdb/photosdb.py:1950-1956`, `photosdb/photosdb.py:2787-2942`), кроме: запись без `ZUUID` и её фото отбрасываются; пустой `ZUUID` или `ZUUID`, который есть и у другой записи или строки `ZGENERICALBUM`, — ошибка `Open`, а upstream оставляет последнюю в одном словаре; значение, которое не читается, ломает `Open`, а `ZSHAREPARTICIPANT` без `ZHASHEDPERSONID` не даёт владельца, тогда как upstream пишет предупреждение и продолжает без общих альбомов (`photosdb/photosdb.py:1953-1956`); из нескольких участников с ролью владельца владелец — с наибольшим `Z_PK`, а `IsMissing` видео решает ресурс подтипа 8 с наибольшим `Z_PK`; upstream берёт последнюю прочитанную строку (`photosdb/photosdb.py:2850-2861`, `photosdb/photosdb.py:2927-2942`). Ни в одной тестовой медиатеке таких записей нет; правила проверены на синтетической медиатеке.
- `Keywords()` и `KeywordsWithoutPhoto()` отсортированы; upstream сохраняет порядок строк. `KeywordCounts` — `map` Go, без порядка по счёту, который есть у upstream (`photosdb/photosdb.py:473-496`, `photosdb/photosdb.py:547-551`). Ключевое слово без названия во всех трёх — `""`; у upstream — `None` (`unicode.py:79-80`, `photosdb/photosdb.py:2006-2014`).
- `BurstAlbumInfoOf` называет альбом один раз. Upstream называет его дважды, если в нём и само фото, и ключевой кадр его серии: это множество объектов `AlbumInfo`, у которых нет равенства (`photoinfo.py:664-671`).
- `AlbumCounts` и `SharedAlbumCounts` считают фото каждого альбома из тех, что отдаёт `Photos()`; пустой альбом добавляет 0. Upstream считает строки членства, включая объекты без строки `ZADDITIONALASSETATTRIBUTES`, обнуляет счёт названия, если пустой альбом с этим названием идёт после другого, и отдаёт словарь по убыванию счёта, а у `map` Go порядка нет (`photosdb/photosdb.py:511-545`, `photosdb/photosdb.py:1873-1901`).
- `PhotoUUIDs` альбома — множество; фото в порядке альбома даёт `AlbumPhotos`. Позиция фото в альбоме `NULL` идёт раньше чисел; upstream падает, если в альбоме есть и то и другое (`albuminfo.py:37-53`, `albuminfo.py:165-187`). `PhotoIndex` фото не из альбома возвращает -1, false; upstream бросает `ValueError` (`albuminfo.py:280-287`).
- У `SystemLibraryPath` нет запасного пути через PhotoKit (`utils.py:206-228`). Если ни один из двух файлов настроек photolibraryd не содержит абсолютный путь без NUL, возвращается `ErrLibraryNotFound`. Upstream возвращает любое значение ключа как есть (`utils.py:180-206`).
- `photokit.Open` проверяет право и возвращает `ErrNotAuthorized`; пользователя он не спрашивает. Он отвергает и `StatusLimited`: upstream читает устаревший `authorizationStatus`, который сообщает об ограниченной медиатеке как о разрешённой (`photokit.py:120-121`), а ограниченная медиатека показывает только выбранные объекты. `RequestAuthorization` спрашивает один раз через `requestAuthorizationForAccessLevel:` и возвращается, как только завершён его контекст, а сам запрос ждёт до срока, без срока — 5 минут; upstream спрашивает в конструкторе `PhotoLibrary` и дважды зовёт устаревший `requestAuthorization:` (`photokit.py:139-160, 1199-1204`). `AuthorizationStatus` возвращает сам статус, а `check_photokit_authorization` — только есть ли право (`photokit.py:113-121`).
- `DB.SharedMomentInfo` и `DB.ShareInfo` (`shared_moment_info` и `share_info` из osxphotos) берутся из строк `ZSHARE`, которые читаются один раз в `Open`; upstream выполняет запрос при каждом обращении (`shareinfo.py:129-148`, `photoinfo.py:1606-1626`), поэтому значение неожиданного типа в `ZSHARE` здесь ломает `Open`, а у upstream — только это свойство. Дата 0 в `ShareInfo` — nil; upstream оставляет там число 0 (`shareinfo.py:74-75`). `DB.ShareInfo` идёт по `ZASSET.ZLIBRARYSCOPE` — ключу, который upstream сам называет догадкой; перенесено как есть (`shareinfo.py:156-165`). Медиатека без таблицы `ZSHARE` не даёт долей, а upstream бросает `OperationalError`.
- `DB.ShareParticipantInfo` и `DB.ShareParticipants` (`share_participant_info` и `share_participants` из osxphotos) дают строки запроса upstream, упорядоченные по `ZSHAREPARTICIPANT.Z_PK`, участника — по разу на строку `ZASSETCONTRIBUTOR`, как его повторяет соединение; upstream выполняет запрос для одного фото при каждом обращении и сохраняет порядок, в котором SQLite отдаёт строки (`shareparticipant.py:21-49`, `photoinfo.py:1634-1649`). `Open` читает и разбирает каждого участника, которого называет `ZASSETCONTRIBUTOR`, один раз, отдельно от его связей с фото, чтобы архив, связанный со многими фото, не читался заново для каждого. Если нет таблицы или колонки, участников нет: upstream перехватывает ошибку запроса; текст в целочисленной колонке такого участника ломает `Open`, даже если его строки `ZASSETCONTRIBUTOR` не ведут ни к одному фото, а upstream передаёт его как есть. Как в upstream, у фото, где `ZNAMECOMPONENTS` одного из участников не разбирается, участников нет (`shareparticipant.py:45-49`); архив со ссылкой за пределы `$objects` не разбирается: `bpylist2` бросает `IndexError`; архив больше 1 МиБ или двоичный список свойств, который отклоняется, как `Z_PLIST` (выше), считается неразобранным, а классы архива не проверяются, как для `Owner` (выше). Часть имени, которой нет в архиве или которая не строка, — `""`; upstream оставляет `None` или само значение, и `share_participants` печатает `None` как `None`. Исходный архив (`_name_components`) не хранится.
- `DB.Comments` и `DB.Likes` (`comments` и `likes` из osxphotos) берутся из строк запроса upstream, которые читаются один раз в `Open` и упорядочены по `ZCLOUDSHAREDCOMMENT.Z_PK`, поэтому комментарии и отметки одной даты сохраняют этот порядок после устойчивой сортировки по дате; upstream сохраняет порядок, в котором SQLite отдаёт строки (`photosdb/_photosdb_process_comments.py:95-150`). Строка, которая называет два объекта, попадает к обоим, как в upstream. Медиатека без таблицы `ZCLOUDSHAREDCOMMENT` или без одной из колонок запроса не даёт комментариев и отметок, а upstream бросает `OperationalError`; для Photos 4 и раньше upstream бросает `NotImplementedError`, а модуль такие медиатеки не читает (`photosdb/_photosdb_process_comments.py:26-39`). Автор без имени — `""`; у upstream — `None`. Значение `ZISLIKE` или `ZISMYCOMMENT`, которое не целое число, ломает `Open`, а upstream читает его через `bool()`; так же ломает `Open` текст в `ZCOMMENTDATE`, который не число, а upstream даёт ему `DEFAULT_DATETIME_LOCAL` (`photos_datetime.py:80-89`).
- `template.Parse` сообщает о синтаксической ошибке смещением в байтах и ожидаемым символом; upstream бросает `ValueError` с текстом TextX (`phototemplate.py:504-507`). Шаблон глубже 32 вложенных выражений — синтаксическая ошибка; upstream ограничен только пределом рекурсии Python.
- `Render` читает поля фото через `template.Photo`. Поле, которое есть в upstream, но которого реализация не даёт, а также `{exiftool}`, `{function}`, `{detected_text}` и `{osxphotos_cmd_line}`, вызывающие программы или код, дают ошибку, оборачивающую `ErrUnsupportedField`; upstream отдаёт значение или `None` (`phototemplate.py:839-884`). Имя, которого в upstream нет, попадает в `unmatched`, как в upstream (881-883). Рендер больше чем `RenderOptions.MaxResults` строк (по умолчанию 10 000) — `ErrTooManyValues`; upstream не ограничен (774-783). Пустые `NoneStr`, `InplaceSep`, `PathSep` означают умолчания upstream (`_`, `,`, `/`): нулевое значение `RenderOptions` — это `RenderOptions()` upstream (388-400).
